Orchestration routing + benchmark

2026-07-27 · feature: orchestration-routing (new, feat-006) · draft · round 0 · branch feat/orchestration-routing-bench

TL;DR

Every brain plan gains a machine-readable orchestration block — which agent and which model runs each phase — that the human edits in the review UI before approving, and that the coordinator reads back after approval instead of improvising. A routing policy (.brain/orchestration.json) makes those assignments repo policy rather than vibes, and lets a phase dispatch to a non-Anthropic CLI (Kimi, Codex) through a shell adapter. Then we prove it: brain bench runs the same fixed task suite through competing routing arms in isolated worktrees and scores them on pass rate and dollars-per-pass — an auditable, in-repo benchmark that doubles as the marketing artifact.

Big picture

Two loops sharing one policy file. The plan loop (left) decides and records who runs what. The bench loop (right) measures whether those choices were actually better. The CLI never spawns a model — it recommends, records, and scores.

The cross-vendor constraint (read before D7)

Checked, because the plan depends on it: Claude Code cannot run a non-Anthropic model as a sub-agent. The Agent tool's model field is an enum of Anthropic aliases (opus/sonnet/haiku/fable), and .claude/agents/*.md frontmatter resolves against the same provider. So "Kimi does the frontend phase" has exactly three implementations:

PathHowMixes vendors in one session?Verdict
Shell adapter A sub-agent with Bash-only tools shells out to the vendor's own CLI in a worktree; returns a diff/commit. Yes — per phase chosen only path with real file-editing agency
MCP wrapper An MCP server exposing "ask model X" as a tool. Yes Advice only — no repo agency unless the server has it
ANTHROPIC_BASE_URL proxy LiteLLM / a vendor's Anthropic-compatible endpoint. No — swaps the whole session Useless for mixed routing; fine as a whole-arm swap in the bench

Consequence for the policy schema: a route names an adapter, not a model string, and every shell adapter carries a probe command plus a fallback route. An un-probeable adapter must degrade to an Anthropic sub-agent and say so in the output — never silently. Also: the exact Kimi model id and endpoint get confirmed by probe at Phase 4, not hardcoded from memory now.

Decisions needed

1. Where does the benchmark live? It is both engineering instrumentation and the marketing artifact, and it writes result state.

OptionProsCons
Code is code, state is brain state — matches how verify.json/runs already split; results show up in timeline Two places to look
One directory; ships with brain init Puts executable task fixtures inside the harness dir — .brain/ stops being just state
Keeps zero-dep CLI lean; benchmarks other harnesses too Second release surface; loses brain ergonomics and brain state access

2. How does the orchestration block attach to a plan artifact? The CLI has to read phase assignments back out after approval.

OptionProsCons
Single self-contained artifact (playbook rule); one source of truth the visible table renders from; trivial, robust extraction by id Agent must keep block and table in sync
No HTML parsing at all; easy to diff Artifact stops being self-contained; two files to keep together
Nothing new for the plan author to write Fragile regex over freeform HTML — rejected on principle

3. How does the human change an assignment in the review UI? ("phase 2 should be Kimi, not Sonnet")

OptionProsCons
Zero new server routes or trust surface; click-only per playbook; agent sees the change and can push back Round-trip through the agent; assignment isn't authoritative until the agent writes it
Human edit is authoritative immediately; no agent turn needed New HTTP route + trust boundary in lib/review/server.js; artifact and store can diverge

4. How does the bench actually invoke an arm? This is the credibility hinge — the numbers are only as good as the isolation and the usage accounting.

OptionProsCons
Vendor-agnostic — a pure-Kimi or pure-Codex arm costs one JSON file; clean process isolation; structured usage/duration in the result payload Nested agent invocation; auth/rate-limit exposure; usage fields must be confirmed by the Phase 0 spike
No nesting; reuses this harness Can't isolate or replay; no per-arm usage accounting; can never include a non-Anthropic arm — kills the whole thesis
Finest-grained telemetry Adds a runtime dependency to a zero-dep repo; Anthropic-only again

5. What repo do bench tasks run against? Needs a pinned base and a deterministic pass/fail script.

OptionProsCons
No external dep; acceptance can reuse brain verify/check; dogfooding is the story; real code, not toy code Tasks skew CLI-shaped; the frontend-UI task is limited to the review chrome
Genuine React/UI surface — the strongest test of a frontend-routing claim External pin, install time, network flakiness inside every run
Fastest, fully controlled, cheap to run often Toy tasks — results won't convince anyone, including us

6. What is the headline number on the scorecard? One metric goes in the README; the rest live in the table.

OptionProsCons
Can't be gamed by being cheap-and-wrong; directly answers "is routing worth it" Meaningless if the spike can't recover real cost — falls back to tokens-per-pass
Simplest, hardest to dispute Ignores the efficiency claim, which is the actual thesis
One tidy number for marketing Arbitrary weights = the arm we like wins; reads as a rigged benchmark

7. Which arms ship in v1? Each arm × task × repeat is real money. Full 4×5×3 matrix = 60 runs.

OptionProsCons
Tests the actual claim (routing > flat delegation) and bounds it top and bottom; one non-Anthropic adapter proves the mechanism Most expensive; the Kimi arm is probe-gated and may skip on a given machine
Cheapest, fastest to green, no vendor auth to solve Proves delegation, not routing — and skips the cross-vendor question that started this
Loudest marketing table Measures models, not our harness — and invites "your benchmark is unfair" fights we'd lose

Benchmark fairness rules (non-negotiable)

These are what separate a benchmark from a marketing chart. They get written into .brain/rules/orchestration.md and enforced where enforceable.

RuleEnforced by
Identical task prompt across arms; only the orchestration directive differs Task prompt lives in task.md, arms may only prepend their directive; runner hashes the prompt and records the digest
Fresh git worktree off a pinned base ref per run — no carryover Runner creates and destroys the worktree; records base SHA in the result
check.sh is written before any arm runs, and never edited to make an arm pass Acceptance script committed in its own commit ahead of the arm configs; result records the check's file hash
n ≥ 3 repeats; report median with min/max and state n. LLM runs are nondeterministic — a single run is an anecdote Runner refuses to emit a scorecard below n=3 unless --preliminary, which stamps the label onto the HTML
Failures publish. No quiet dropping of a bad arm or a bad run Every run's raw JSONL committed under .brain/bench/; report prints an excluded[] block with reasons or none at all
An arm that vandalizes the harness doesn't get credit for passing Post-run brain check + brain verify in the worktree; a dirty harness downgrades the run to FAIL
Skipped external arms are visible, never silent Adapter probe failure records status: skipped-unavailable and prints in the report

Plan of record

Double-click a phase to rewrite it, x to drop it, or add one below. Phase 0 is a gate: if it fails, phases 4–5 change shape and we say so instead of building on a guess.

  1. Phase 0 — spike, the metrics gate. One throwaway headless run of one arm on one task in a worktree. Acceptance: we can name, from real output, the pass/fail, wall-clock, token counts and (if available) cost of a run — or we document which of those is unobtainable and pick the fallback metric before writing any runner code.
  2. Phase 1 — routing policy + brain orchestrate. .brain/orchestration.json (adapters, routes, probes, fallbacks) plus orchestrate / orchestrate probe. Acceptance: brain orchestrate prints the routes as TOON with a help: list; probe reports each adapter available/unavailable and never exits nonzero for a missing optional CLI; unknown flags exit 2; skill --check passes after skillContent() is updated.
  3. Phase 2 — plan integration. Orchestration section added to the plan playbook, embedded JSON block read by brain orchestrate plan <slug>, brain check warns (never fails) on a plan with no block. Acceptance: this very plan's block round-trips — orchestrate plan 2026-07-27-orchestration-routing-bench prints the phase→agent→model table; the 5 existing plans still pass brain check.
  4. Phase 3 — execution attribution. runs append records which agent/model produced a step; brain watch surfaces it. Acceptance: a step appended with --agent builder --model sonnet renders in the run note and the dashboard; omitting the flags stays valid (backward compatible with existing run notes).
  5. Phase 4 — bench runner + task suite. Two tasks first (one CLI-shaped, one UI-shaped), the v1 arms, brain bench run with --max-usd / --dry-run / --repeat. Acceptance: a dry run prints the full run matrix and cost ceiling without spending a cent; a real 2-arm × 1-task × n3 run produces 6 result JSONs with acceptance verdicts, and a deliberately-sabotaged arm is recorded FAIL rather than crashing the runner.
  6. Phase 5 — scorecard + README. bench report (TOON) and --html (standalone scorecard, same editorial palette), README section with the real numbers and the fairness rules linked. Acceptance: scorecard renders offline with n, medians and spread per arm; refuses to drop the preliminary stamp below n=3; README quotes only numbers present in committed result files.
Why not build the bench first, since it's the point?

The bench needs something to compare. Arms are defined in terms of the routing policy (Phase 1) and the orchestration directive (Phase 2) — without those, "policy-routed" isn't a configuration, it's a prompt written by hand differently each run, which is exactly the unmeasurable state we're trying to leave. Phase 0 still de-risks the expensive part first.

Orchestration for this plan (dogfood)

The extra step, applied to itself. This is the human-editable assignment table; the same data lives in the embedded JSON block at the bottom of this file. Routing rationale: schema and CLI surface decisions stay with the coordinator (they set the contract everything else depends on); mechanical CLI work and docs go cheap; the runner is the one phase worth a strong model on its own; the UI-shaped bench task is where the non-Anthropic adapter earns its keep or doesn't.

Error paths

FailureDetected byHandled byHuman sees
External CLI not installed (no kimi on PATH) adapter probe exits nonzero route degrades to its declared fallback adapter: kimi (unavailable) → fallback sonnet in the orchestrate output; exit 0
No .brain/orchestration.json in a brain policy loader finds no file built-in default routes used TOON marked source: default + help: line offering to scaffold one; exit 0
Plan artifact has no orchestration block orchestrate plan / check finds no #brain-orchestration warning, not failure — all 5 existing plans predate this warn: plan <slug> has no orchestration block; check stays exit 0
Malformed policy (shell adapter with no probe, unknown route kind) schema validation in policy.js, run as a verify.json check refuse to dispatch error: + the offending key path, exit 1
Bench run exceeds the budget ceiling runner sums per-run cost against --max-usd before each launch stop launching; keep completed results halted: budget with the count run vs planned; partial results still reported
Arm hangs per-run timeout (default 15 min, like verify's per-check timeout) kill the process tree, tear down the worktree, record status: timeout timeout row in the report, counted as a failure not a skip
Arm leaves the worktree dirty or breaks the harness post-run brain check + brain verify inside the worktree downgrade the run to FAIL with reason: harness-dirty FAIL row naming the failed invariant — passing by vandalism doesn't count
Worktree cleanup fails (locked, disk full) nonzero git worktree remove record the leaked path; keep going leaked_worktrees[] block + the git worktree prune command to run
Cost/usage unavailable from an arm's output Phase 0 spike, or a null usage field at runtime fall back to the tokens-per-pass metric; mark the arm's cost column unknown scorecard shows unknown — never an imputed dollar figure

Testing plan

No test framework in this repo — every line is a CLI invocation with an asserted exit code and eyeballed TOON, per CLAUDE.md. Add or edit items inline.

  • Golden: brain orchestrate prints routes as TOON with a help: list; --help and --brain both work; an unknown flag exits 2
  • Golden: orchestrate plan 2026-07-27-orchestration-routing-bench round-trips this file's embedded block into the phase table
  • Error: probe with kimi absent from PATH → fallback row, exit 0, no stack trace
  • Error: malformed orchestration.json (shell adapter, no probe) → exit 1 naming the key path
  • Regression: all 5 existing plans and brain check stay exit 0 with no orchestration blocks present
  • Regression: runs append without the new --agent/--model flags still writes a valid step; existing run notes still render in watch
  • Regression: brain skill --check and brain verify --brain .brain both exit 0 after the new commands land
  • Golden: bench run --dry-run prints the full matrix + cost ceiling and spends nothing
  • Error: sabotage drill — an arm that deletes a tracked file is recorded FAIL harness-dirty, and the runner survives it
  • Error: budget drill — --max-usd set below one run's cost halts before launch with partial results intact
  • Golden: real 2-arm × 1-task × n3 run produces 6 result files; bench report shows medians + spread + n; the HTML scorecard renders offline (no network)
  • Error: bench report below n=3 refuses to drop the preliminary stamp
  • Verification doc per playbook verify for the review-UI change (orchestration section + attribution in watch), with screenshots

Open questions

  • Who pays for bench runs, and does it ever run in CI? A nightly matrix is a real recurring bill; local-only-on-demand is free but the numbers go stale and nobody trusts a stale benchmark.
  • Do external-vendor API keys belong anywhere near this repo's config, or must adapters read only from the ambient environment? (Leaning strictly ambient — the policy file names a probe and a command, never a secret.)
  • Is the routing taxonomy (architecture, frontend-ui, tests, mechanical, docs, review) the right cut, and who assigns a phase's kind — the plan author, or inferred from the files it touches?
  • Should the bench also measure the human cost — review rounds, prompts per plan, interventions — since "fewer rounds to approval" may be the more honest harness win than dollars per task?
  • Does a published benchmark naming other vendors create a claims-accuracy obligation we want (reproducible, auditable) or a fight we don't (vendor pushback on task selection)?
