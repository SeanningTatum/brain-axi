Launch readiness — brain-axi

2026-07-30 · feature: launch-readiness (proposed) · reviewed · round 1

TL;DR

brain-axi is not on npm, and the skill we tell people to install invokes npx -y brain-axi 23 times — so the documented install path 404s for everyone who is not you. This plan publishes it, moves the pitch onto the one surface nothing else does well (human-in-the-loop plan and screenshot review, which already runs with no .brain/ at all), and closes the two credibility gaps a first-time reader hits: a home dashboard listing dead sessions, and zero self-verification. Five phases; the thin tier is phase 1 alone.

Product brief

Problem + evidence

A person who wants to try this cannot. Four checkable observations:

ObservedCommand runResult
The package does not exist on the registry npm view brain-axi version E404 'brain-axi@*' is not in this registry
The installed skill depends on that package on every line grep -c "npx -y brain-axi" .claude/skills/brain/SKILL.md 23 invocations, all currently dead
The harness has never planned its own distribution brain search "npm publish" 0 matches in .brain (null result, across 23 checkpoints and 9 plans)
The first screen a new reader sees is already wrong brain (home) + file-existence check on each row 11 open sessions, 6 pointing at files that no longer exist — /private/tmp/brain-review-demo/plan.html, …/posthog-analytics-plan.html, pw-artifact-debug|runA|runC.html, ZZ-demo-ux.html

A fifth, about the tool's own claim on reliability: brain search "test framework" returns 8 matches, every one of them asserting there isn't one — including the standing rule at codebase/programming-model.md:58, "Do NOT add an npm dependency, a build step, or a test framework." A harness whose pitch is that it makes agents verifiable currently verifies itself by being run by hand. That rule is a real constraint, not an oversight, so phase 4 asks to amend it explicitly rather than quietly breaking it (technical decision 1).

User + job to be done

Two, and they want different things:

The evaluating agent, first contact. It has been told "write the plan and review it with me," it is sitting in a repo with no .brain/, and its job is to get a human looking at a plan in the browser without mutating the repo or asking permission to scaffold a directory. Today that agent fails twice over: the command resolves to a 404, and even from a checkout, review refuses to run without a .brain/.

Correction, found while executing phase 2. An earlier version of this section claimed review already worked with no brain, reasoning from cmdReview (bin/brain.js:2209) never calling findBrain and session state living in ~/.brain-axi/state.json (lib/review/store.js:20). Both facts hold and the conclusion was still wrong: the CLI posts to the review server, and /api/open hard-requires a brain at lib/review/server.js:778-784 before persisting a plan record via ensurePlan(brain, …). Verified by running review from a scratch directory: error: no .brain directory found walking up from …. So product decision P2 ("guarantee it") is an implementation task, not a documentation one — 10 reads of session.brain in server.js need null handling, plus a sidebar empty state, plus the session-record shape in docs/REVIEW-ARCHITECTURE.md.

The returning maintainer agent, session start. It runs brain (or gets brain context from the SessionStart hook) and wants the dashboard to be true, because it makes its next move from that output. Today 6 of 11 session rows are noise it has to learn to ignore — and an agent that learns to ignore one row of a dashboard discounts the rest of it too.

Non-goals

  • Not deleting or deprecating the memory layer. A reader seeing "reposition off memory" would reasonably expect .brain/ to get cut. It doesn't — it stays the substrate and this repo keeps dogfooding it. What changes is that it stops being the entry fee.
  • Not the watch dashboard's live-watcher CTA. Reasonable to expect, since phase 5 touches the annotate loop. Declined because plan 2026-07-17-annotation-watch-runner (draft, bound to feat-004) already owns that decision set — transport, runner start policy, CTA wording. Re-deciding it here would fork a decision that already has a plan waiting on review.
  • No pricing, hosting, or telemetry. MIT CLI stays an MIT CLI. Distribution is the bottleneck; value capture is a different problem and putting it in scope would make every phase above negotiable.

Product decisions

What we are building, before how. Each card has a recommendation and the reasoning behind it — click one and queue it.

1. What is the headline job on the README and in the skill's opening lines?

OptionProsCons
Uncontested ground; works with zero setup and zero repo mutation; 30-second time-to-value from one command Demotes the subsystem the last 23 checkpoints were spent on
Matches where the code volume actually is; no doc churn Competes head-on with ~6 named tools and the host runtime's own memory; entry fee is adopting a directory
Nothing gets demoted; honest about the two halves Two headlines is no headline — the reader picks neither and the first command is ambiguous

2. Should "works with no .brain/" be a guaranteed, advertised promise — or an undocumented accident that happens to hold today?

OptionProsCons
The zero-commitment entry the whole repositioning rests on; a test stops a future refactor from adding a findBrain call and silently killing it Pins a behavior that is currently free to change
Zero work The pitch's load-bearing claim has nothing holding it up; one refactor away from a broken README

3. What name do we publish under?

OptionProsCons
Registry says the name is free (E404); every existing doc, skill line, and playbook string already points here — zero rewrites No namespace protection against a similarly-named package later
Ownership unambiguous; name can never be sniped Rewrites 23 skill lines plus every playbook and README string, and npx -y @scope/name reads worse in the one command we most want a stranger to type

4. What should brain home do about a session whose artifact file is gone?

OptionProsCons
Dashboard is true immediately with no data loss; a file on an unmounted volume reappears rather than being destroyed; deletion stays a deliberate act Two concepts (hidden vs pruned) for the reader to hold
One concept; state self-heals Destroys review history for a file that is merely moved or on an unmounted disk — irreversible, and the round records are the thing worth keeping
Smallest change; home stays literal Leaves M2 at 6 of 11 until somebody remembers to run a command — the dashboard keeps lying by default

Decisions needed

How, given the answers above.

1. codebase/programming-model.md:58 says "Do NOT add an npm dependency, a build step, or a test framework." Phase 4 needs tests. Which way?

OptionProsCons
Honors what the rule was protecting (no dependency, no build step, no bundler) while dropping the part that was protecting nothing; node --test ships with Node 18+ Amends a standing rule, so the rule doc and HARNESS.md must both be edited in the same commit
No rule amendment; reuses the verify.json registry that already exists Reinvents a test runner in bash; no per-assertion reporting; the "no test framework" rule survives in letter while being violated in spirit
Zero work; matches the rule exactly as written Leaves M3 unmet and the credibility gap open — this is the gap a reliability tool can least afford

2. How does a publish actually happen? package.json currently has no scripts at all, which is itself a stated property of this repo.

OptionProsCons
Keeps package.json script-free as documented; the human stays in the loop on an irreversible, public action Nothing mechanically forces brain verify before a publish — it's a documented step, not a gate
Publishing a red build becomes impossible Adds the repo's first npm script, contradicting a documented property; also runs on every local npm pack
Reproducible; release notes and publish in one place Needs a stored npm token and makes the first publish depend on CI that does not exist yet — more moving parts than the thin tier wants

3. What version does the first publish carry?

OptionProsCons
Honest: 21 commands in 17 days with no external users is not a stable surface, and pre-1.0 says so without a paragraph of caveats Some readers discount pre-1.0 packages on sight
Reads as finished; semver breaking-change discipline starts now Commits to a command surface no outside user has touched yet; every rename after this is a major bump

4. Phase 5 (shots poll) already has a plan of its own — 2026-07-17-annotation-watch-runner, bound to feat-004, never reviewed. How do the two relate?

OptionProsCons
One decision lives in one place; that plan's transport card (long-poll vs fs.watch vs hybrid) is more considered than anything this plan would restate Gold tier then depends on a second review round happening
One review round, one artifact to track Discards a written plan that already framed the problem better, and stretches this plan past launch readiness into feature work
Tightest possible plan; launch readiness only Ships a half-closed feedback loop — the README currently advertises it as "planned, not yet shipped," which is the kind of promise a new reader checks

Plan of record

Tier boundaries land on phase boundaries: stop after 1 for thin, after 3 for complete, after 5 for gold. Double-click any phase to rewrite it; x to cut it.

  1. Phase 1 — publish. Add a files allowlist (bin, lib, README.md, LICENSE) so the tarball stops carrying .brain/, plans/, and stray root HTML; set the version; publish; smoke it cold. Acceptance: npm pack --dry-run lists no .brain/ or plans/ entry; npm view brain-axi version returns the published version; from /tmp/fresh with nothing on PATH, npx -y brain-axi review plan.html exits 0 and opens a session (M1).
  2. Phase 2 — reposition the entry point. README leads with the review one-liner; .brain/ moves to an "if you want it to remember" section; the skill's opening section leads with review; brain review run outside a brain repo gains a help: line offering brain init. Acceptance: README's first code block is the review command; brain review from a directory with no .brain/ prints that help line and still exits 0; brain skill --check clean after regeneration.
  3. Phase 3 — session hygiene. Home hides sessions whose artifact file is missing and reports the hidden count on one line; brain review prune deletes them on request and reports what it removed; brain check gains a row asserting every listed open session resolves. Acceptance: home shows 0 dangling rows and a hidden: 6-style line (M2); review prune reports 6 removed; the new check row appears and passes. Added during execution: the same rot has a second source — reopening a plan without --plan re-derives the slug from the filename and mints a date-prefixed shadow record, so brain plans lists 2026-07-29-2026-07-28-ai-work-harness (draft, 0 rounds, meta.json only) beside the real ai-work-harness (reviewed, 2 rounds). Reproduced and reverted while smoke-testing this plan. Acceptance extends to: reopening an already-recorded artifact binds to its existing plan slug instead of creating a second one.
  4. Phase 4 — self-verification. A node:test suite of at least 20 assertions covering the TOON encoder, parseArgs unknown-flag rejection (exit 2), parseProgress separator splitting, set-status one-in-progress enforcement, the 0/1/2 exit contract, store.js corrupt-state.json recovery, and the no-.brain/ review promise from product decision 2; registered in verify.json as tests; one GitHub Action running check, verify, skill --check. Acceptance: brain verify reports 3/3; the Action is green on push; the amended rule is committed alongside (M3).
  5. Phase 5 — close the annotate loop (gold). Implement brain shots poll <feature> per feat-004, with transport as decided in plan 2026-07-17-annotation-watch-runner — this plan does not re-decide it. Acceptance: a pin sent from the watch carousel returns from a blocking shots poll within 2s; annotation-watch flips shipped with evidence; the README's "planned, not yet shipped" note is deleted.
    Why is this last rather than first?

    It is the most interesting engineering and the least urgent product work. Nobody can reach it until phase 1 makes the tool installable, and it is the one phase that depends on a separate plan's review round — so it sits where a slip costs the least.

Testing plan

Open questions

  • Should the review server auto-increment off 4517 on EADDRINUSE instead of erroring with a --port hint? A stranger's first command failing on a port collision is a bad first impression, but silently moving ports makes the URL unpredictable.
  • Should review in a non-brain repo offer brain init in a help line (recommended in phase 2) or actually prompt for it in a TTY, the way init --agents-md already does?
  • How much of the memory layer stays in the README at all? There is a version of "review-first" that buries .brain/ so deep that the thing this repo has spent 23 checkpoints on becomes invisible.
  • Sequencing against one_in_progress_at_a_time: ai-work is in-progress with empty evidence. Does launch-readiness wait behind it, does ai-work get shipped or marked blocked first, or do phases 1–3 run without claiming in-progress at all?
