Harness hardening — state integrity in brain-axi, then the template

2026-07-31 · feature: state-integrity · draft · round 0

TL;DR

An audit of the cf-saas-starter harness — cross-checked by an independent Codex pass that read the brain-axi source — landed at 5/10. The process scaffolding is good; the state layer's invariants are not enforced, and two of the three named harness defects from the literature are live in the repo today and pass every gate. We fix brain-axi first so every install inherits the fix, then wire the template to consume it.

Product brief

Who it's for: any agent operating a .brain/ harness, and the human who has to trust what it reports. brain-axi is a CLI someone invokes and whose output format is a contract, so this is a user-facing change, not an internal refactor.

The job it does today: tells you what's in flight, what shipped, and whether the harness is coherent.

What breaks that promise: it can report coherent while holding a contradiction. brain check answers "is the harness intact?" and is routinely read as "is the harness working?" Those are different questions and only the first is implemented.

Behavior change the user will actually notice: brain ship stops flipping state when checks fail (today it flips anyway and says so), and brain check starts failing on brains it used to pass.

Plan of record

  1. Phase 1.0 — make the CLI verifiable. Acceptance: scripts/check-state-invariants.mjs builds synthetic brains in a temp dir and asserts brainCheck verdicts; registered in .brain/verify.json; brain verify --stage baseline green.
    Why first?

    brain-axi has zero automated tests by policy. Every later item is unfalsifiable without this, and "eyeball the TOON" does not survive a refactor of the thing producing the TOON.

  2. Phase 1.1-1.2 — schema + preflight ship + atomic writes. Acceptance: brain check fails on duplicate slugs, bad status, shipped-without-evidence; ship against a failing brain leaves feature_list.json byte-identical (git diff empty) and exits 1; all three writers go through writeFileAtomic.
  3. Phase 1.3-1.5 — one verdict parser, commit-bound evidence, shipped⇒PASS. Acceptance: the template's OTEL doc reports PASS from both readers; unknown is a failing row; docs without the frontmatter block report legacy not fail; --strict flags the 2-of-7 coverage gap.
  4. Phase 1.6-1.9 — state-only init, metrics, generated index, small defects. Acceptance: init --state-only on a copy leaves rules/ + recipes/ intact and brain check green; brain metrics non-empty after three verify runs.
  5. Phase 2 — template consumes it. Acceptance: .brain/verify.json declares the real gates and /verify-done calls the registry; the AST checker catches all four fixtures grep missed; new e2e specs green; design-critic suite clears its threshold; fresh clone yields an empty cursor.

Golden path

  1. Agent finishes a feature and runs brain verify --stage verify. Each check's {status, exit, seconds} appends a row to gates.jsonl stamped with branch + commit.
  2. Agent writes a verification doc with the brain:verification block — verdict, the commit it was verified at, the commands and their exit codes, the screenshots.
  3. brain ship <slug> --evidence "…". It projects the next state, runs brainCheck against the projection: schema valid, one-in-progress honored, doc paths resolve, verdict parses to PASS, screenshot links resolve.
  4. All pass → atomic write of feature_list.json, checkpoint appended, exit 0.
  5. brain metrics now answers "did the gates catch anything, and how often did we pass first try" — the question the harness could not answer before.

Testing plan

  • Synthetic brains: {}, [], "hello", duplicate slug, duplicate id, unknown status, shipped-without-evidence — each must produce a specific failing row, not a crash and not a pass.
  • Both verdict styles (emoji and bare word) parse identically from both readers.
  • ship atomicity proven with git diff after a failing preflight.
  • init --state-only on a copy of the template brain: state gone, stack docs intact.
  • AST checker fixtures that must each fail: throw err, bare try {}, single-quoted zod import, a new untested exported helper.
  • Clone simulation: fresh clone → bun setup → brain progress returns an empty cursor, not v1.6.0.
  • Regression: the template's ./scripts/harness-check.sh still passes 10/10.
  • Regression gate (evals): every frozen case must pass — a frozen failure is an unconditional fail regardless of aggregate. Aggregate gets aggregate_tolerance: 0.02 against the prior run. Revert trigger: any frozen case flips, or the held-out slice drops while the visible set improves (that pattern means the prompt was fit to the test).

Open questions

  • Does --strict get a deprecation date, or live indefinitely as an opt-in? Leaning: one release, then default, then delete the flag.
  • Should brain check gain a machine-readable --json output for CI, or is the TOON contract sufficient to parse?
  • Cross-client hook parity (Codex, Cursor, Aider get no rule routing) — documented as a known limitation for now. Worth its own plan?
  • EVAL_KINDS is validated but never branched on. Honor it, or relabel it as metadata?
