Honest review — brain-axi vs lavish-axi

2026-07-30 · feature: none (positioning) · draft · round 0

TL;DR

We have a real product with a clean moat and no distribution. lavish-axi has distribution, engineering discipline we don't have, and — critically — already owns the exact ground we just decided to make our headline.

The approved P1 decision ("review-first is the headline") points us at a 2,379-star incumbent's core feature, shipped 43 times, built by the same author whose AXI standard we vendored last week. Meanwhile the thing lavish has no answer for — the .brain harness — is what we're about to demote to the second act. I think that's backwards, and this review asks you to settle it.

Read that honestly: on the pure artifact-review loop we are at feature parity with a few gaps in their favour, using their vocabulary, one week after vendoring their standard. brain playbook plan §9 credits "lavish-axi's own input playbook" by name, and §9.4 lists which of their patterns we deliberately did and did not port. That is not plagiarism — it's an ecosystem, they published the standard for exactly this, and we attributed it in THIRD-PARTY-NOTICES.md. But it does mean a review-first headline invites the one comparison we lose.

Where we actually win

lavish-axi's README, checked directly: no persistent project memory, no feature tracker, no progress checkpoints, no rules/recipes docs, no verification evidence, no evals. Nothing in their twelve commands writes durable state about the project. Their session state is a session.

Ours is the opposite. .brain/ today, in this repo, dogfooded: 7 features with an enforced one-in-progress policy, 29 checkpoints, 39 docs across rules/recipes/codebase/architecture, 3 verification verdict docs, an eval suite of 37 cases, 10 plan records with review rounds, and 13 deterministic invariant checks that hold it together (brain check 13/13, brain verify 3/3 right now).

And the thing neither of us has written down as a product claim yet: our review sidebar shows that memory while the human reviews. The reviewer sees past plans, the timeline, and feature state next to the artifact. lavish reviews an artifact; we review an artifact in the context of the project's history. That sentence is the product.

Two smaller genuine wins: zero runtime dependencies against their seven (our whole install is one file tree, no express, no build), and a Node 18 floor against their 22 — we run in more places, more cheaply, with a smaller supply-chain surface.

Product decisions

1. What is the headline, given lavish-axi exists?

This re-opens approved decision P1 of launch-readiness. I'm re-opening it deliberately: P1 was decided before anyone had put our review surface next to theirs, and the comparison changes the input.

OptionProsCons
Leads with the one thing lavish has no answer for; keeps the zero-setup first run P1 was actually buying; the sidebar-shows-memory behavior already exists and nothing else on the market does it A compound claim is harder to fit in one line than either half
Zero-setup value on the first command; matches the skill and package.json already on this branch Invites a head-to-head we lose on Excalidraw editing, export, share, 43 shipped versions and 2,379 stars
Cheapest; strongest differentiation; README already written well First command requires a .brain — the setup-before-value problem P1 was approved to fix

2. Do we compete with lavish-axi on artifact review, or interoperate?

They publish axi-sdk-js and consume it; we hand-rolled lib/review/sdk.js (1,442 lines) covering similar ground. Their author wrote the AXI standard we vendored.

OptionProsCons
Naming a 2.4k-star neighbour as complementary borrows credibility instead of picking a fight; honest about where we came from; readers self-select correctly Concedes the artifact-editor crown explicitly; some users will install theirs instead
One tool, no hand-off Excalidraw + mermaid-to-excalidraw + React is their entire dev dependency block — porting it ends zero-deps, our clearest technical win, to chase parity on their turf
No comparison to lose Anyone in this ecosystem finds them in one search and draws their own conclusion about why we didn't mention the standard's author

3. What engineering floor do we hold before publishing 0.2.0?

Their npm run check is build + lint + format + typecheck + test + skill-drift, wired into 4 workflows and release-please. We have verify (3 checks) and check (13 invariants) and no CI running either.

OptionProsCons
Asserts the exact things that are broken today (findings 1, 2, 3); stdlib-only per approved P5, so zero deps survives; one phase No lint or formatter — style stays by convention
Contributor-ready; catches a class of bugs we currently can't see Four devDependencies and a config surface on a project whose pitch is "nothing to install, nothing to break"; delays publish
Fixes the biggest user-facing break (finding 1) today Publishes an immutable version with no test asserting any of its claims — the situation that produced finding 2

Plan of record

Assumes the recommended answers above. Phase 1 is unconditional — those things are broken under every option.

  1. Phase 1 — commit what's already true. Commit the uncommitted launch-readiness phase-1 work (LICENSE, files allowlist, 0.2.0, repository/homepage/bugs/keywords) as its own PR, minus the no-.brain claim until phase 3 backs it. Acceptance: gh api reports license MIT not null; npm pack --dry-run still 16 files with no .brain/ or plans/; brain skill --check clean.
  2. Phase 2 — settle the story on every surface. Rewrite README, skill description and package description to one headline per decision 1, add the lavish-axi relationship paragraph per decision 2, fix the single-file claim and regenerate the stale quick-start output. Acceptance: all three surfaces state the same headline; no sentence in README or SKILL.md is falsifiable by running a command.
  3. Phase 3 — make the zero-setup on-ramp real. Null-brain review sessions: guard the ~10 session.brain reads in server.js, a sidebar empty state that names brain init, and the nullable brain in docs/REVIEW-ARCHITECTURE.md. Acceptance: from a scratch dir with no .brain, brain review p.html exits 0, a full annotate-send-poll round completes, and no file is written in the scratch dir.
  4. Phase 4 — session hygiene. Per approved P4: home hides sessions whose artifact is gone, brain review prune deletes them explicitly, a new check row counts them, and reopening stops minting date-prefixed shadow plan records. Acceptance: home shows 5 sessions not 10; check goes to 14 rows and stays green.
  5. Phase 5 — CI, tests, publish, release. node:test suite asserting the shipped skill's promises per decision 3, amend the no-test-framework rule at codebase/programming-model.md:58, first GitHub Actions workflow running verify + check + the suite, then npm publish 0.2.0 and tag the release. Acceptance: workflow green; npm view brain-axi version returns 0.2.0; npx -y brain-axi --help works from a scratch dir with no clone.

Testing plan

Open questions

  • lavish went from 0 to 2,379 stars in about ten weeks. Do we know how — Show HN, a Twitter thread, an Anthropic mention? Whatever channel worked for them is the one distribution question that matters more than anything in this document, and I have no evidence about it.
  • Should we adopt their published axi-sdk-js instead of maintaining our own 1,442-line lib/review/sdk.js? It would end zero-deps but put us on the standard's reference implementation and cut a maintenance burden.
  • Is there a version of this where .brain itself is the product and the review UI is optional — i.e. brain-axi ships the memory harness and explicitly recommends lavish for artifact review? That's the most honest read of our comparative strengths and the biggest strategic swing.
  • ai-work is the one in-progress feature and the one-in-progress policy blocks claiming another. Does this land as a new feature, or as a revision of the launch-readiness plan?
