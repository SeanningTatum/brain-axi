Product-grade planning — mockups, UX flows, and a product-expert planner

2026-07-30 · feature: planning-ux (proposed) · draft · round 0

TL;DR

Plans today are engineering-shaped: architecture, phases, files, tests. Two things are missing before a human can actually approve one — what the thing looks like (screens, states, the flow between them) and why this is the right product bet (who it's for, what success is, what we're deliberately not building). This adds both to the planning surface: a wireframe + UX-flow section in the plan artifact, and a standing product playbook that makes the planner argue like a product lead — surfacing decisions with a recommendation and a rationale instead of asking the human to invent the options.

Context

Six playbooks exist today (start, plan, ai, verify, execute, done), all printed verbatim by brain playbook <id> from lib/review/playbooks.js (1,943 lines). The plan playbook is 12 sections + an AI addendum (§13). None of the 13 mention UI, screens, states, users, or success metrics — the closest is §9 "golden path", which is a request sequence diagram, not a user journey.

Prior art in this repo that this builds on, not around: plan 2026-07-16-shot-carousel-annotation (reviewed, 1 round) shipped the screenshot carousel; commit bc63b0b shipped pin-drop annotation on artifact reference images — so a reviewer can already drop numbered pins with notes onto an image inside a plan. The ai playbook (feature ai-work, in-progress per the 2026-07-29 checkpoint) established the precedent this follows exactly: a new standing playbook + conditional branches folded into the existing bookends + skill regeneration + eval cases.

Blocking constraint: feat-006 ai-work is in-progress and policy.one_in_progress_at_a_time is enforced by brain check. This feature cannot be claimed until ai-work Phase 4 ships. See §Error paths.

UX flow

Why HTML and not an image: an inline wireframe is annotatable per-element (the SDK already handles element clicks), diffs in git, costs zero tokens to regenerate, and renders offline. Images get pin-drop, which is better for dense visuals — both paths stay available (decision 2).

Decisions needed

1. How do the two capabilities get packaged? Playbooks are read whole; the plan playbook is already ~880 lines.

OptionProsCons
Mirrors how ai shipped; each loads only when relevant; plan stays skimmable Two more ids to keep in skill sync; agent must follow a pointer
One read, nothing to miss Plan playbook grows past ~1,300 lines; every plan pays the tokens even when there's no UI
Smallest surface The wireframe kit is the bulkiest part — folding the bulky half is backwards

2. What fidelity and medium for mockups? This sets how much token budget every UI plan spends and how much a reviewer can actually judge.

OptionProsCons
Cheap to emit and revise; per-element annotation; offline; forces layout/flow critique instead of color bikeshedding Can't judge visual design; a reviewer may approve a layout they'd hate styled
Approve the real thing; fewer surprises at verify Expensive per revision; drags planning into visual-design rounds; clashes with the plan's own editorial palette
Right tool per plan Two kits to document; agents will guess wrong about when to escalate

3. When are the product + UX sections required? A required section that doesn't apply becomes ritual; an optional one gets skipped.

OptionProsCons
Same trigger idiom the harness already teaches; no ritual on a refactor plan Agent has to judge "is this user-facing" — judgment can go soft
No judgment call; forces "who is this for" on every plan, including CLI-only ones Empty ceremony sections train agents to fill boxes with mush
Zero friction Will be skipped exactly when it matters most; no gate = no behavior change

4. What does "planner as product expert" actually enforce? The difference between a real gate and a vibe.

OptionProsCons
Forces the "are we building the right thing" argument before phases exist; scope tiers give the human a cut lever Longest section; a weak planner can still write plausible filler
Fast; covers the 80% No scope-tier lever — the human can only approve/reject, not cut
Hardest to fake Most repo work has no instrumented metric; degrades to guesses

5. Product decisions — separate section or merged? Today §5 "Decisions needed" is one undifferentiated pile.

OptionProsCons
The human answers "what are we building" before "how"; a bad product answer invalidates the technical cards below it Some decisions are genuinely both; agent must pick a home
No structural change; a chip carries the signal Ordering isn't enforced, so the "why" can land after the "how"

6. Does an approved mockup become verification evidence? The verify playbook already drives a browser and stores screenshots via brain shots.

OptionProsCons
Closes the loop: approved-at-plan becomes checked-at-done; reuses shots + pin-drop wholesale New persistence surface; can slip without blocking phases 1–3
Nothing new to store; smaller diff Nothing stops shipped UI from drifting from what was approved

AI addendum

Playbook text is a prompt — it is the instruction an agent reads before producing an artifact — so §13 applies.

Prompt contract

PromptJobOutput the caller parsesFailure modes
playbook productMake the planning agent argue the product case before the technical one Product sections in the plan HTML + product decision cards Plausible filler; invented metrics; non-goals that are really unstated goals
playbook uxMake the agent emit annotatable screens, states, and a flow Wireframe HTML + state matrix + flow diagram Missing empty/error states; controls without data-brain-action; decorative mockups that don't match the plan of record

No model call is added by this feature — both playbooks are static text served by the CLI, so there is no model pin, no cost delta, and no latency delta.

Eval plan + regression gate

Suite: skill-coverage (31 cases, 28 frozen, baseline 1.000 as of the 2026-07-29 checkpoint). New cases assert both playbook ids are documented in the generated skill and that the plan playbook names its UX/product triggers. Gate: the aggregate may not fall below 1.000 and no frozen case may regress — a frozen failure reverts the change regardless of the aggregate.
