Skills on top, SQLite underneath — brain-axi as a plugin

2026-10-09 · feature: (new) skills-plugin + sqlite-engine · tier: full · reviewed · round 1

TL;DR

Move the method (the 10 playbooks, ~209KB of prompt text in lib/review/playbooks.js) out of the CLI and into 11 superpowers-style skills that trigger by description and hand off to each other, shipped as a Claude Code plugin next to the npm CLI. Separately, replace the file-based .brain/ with a single SQLite database (node:sqlite, zero npm deps) for new brains, with FTS5 search from day one. Skills ship first because they don't depend on storage.

Product brief

Problem + evidence

  • The method only shows up if the agent asks for it. A playbook loads only when the agent remembers to run brain playbook <id>. The 31KB brain skill exists mostly to tell it to do that.
  • Each load is huge. This session: brain playbook plan printed 54,673 bytes and Claude Code moved it to a file ("Output too large (53.4KB)"). Sizes today: plan 54.7KB · verify 27.9KB · product 23.1KB · ux 23.0KB · execute 21.5KB · ai 21.4KB · done 10.4KB · start 9.5KB · grill 8.8KB · write 8.2KB.
  • Editing prompt text means editing code. Every wording change touches playbooks.js and has to pass the skill --check sync gate.
  • Storage limits search. brain search scans every file linearly and keeps 20 rows. The 2026-07-16 plan flagged home, context, runs and docs listings as unbounded. You want indexing available later without another rewrite.

User + job

Mainly the coding agent working in a repo that has a brain: Claude Code only for now (round 1: codex/opencode deferred). Its job is to do the right step of the method at the right time without being told. Second, Sean, who maintains the method and wants to edit it as markdown and install it with one command.

Success metric

  • Countable: starting a plan loads ≤ 10KB (the brain-plan SKILL.md) instead of 54.7KB. Reference files load only when a section needs them. Checked with wc -c skills/*/SKILL.md and a cap enforced by brain skill --check.
  • Countable: brain context (runs on every session start) stays ≤ 600 bytes. It's 473 today; the cap keeps it there.
  • Behavior: in a fresh Claude Code session in a repo with a brain, asking "plan X" loads brain-grill, then brain-plan, with no brain playbook call. Checked by the new skill-routing eval (AI addendum).

Non-goals

  • Not adopting obra/superpowers itself. We borrow its design, not its skills or its startup hook.
  • Not migrating existing file-based brains. This repo's brain gets deleted and re-scaffolded on the new engine instead (round 1). Its history stays recoverable in git.
  • No codex/opencode support in this plan (round 1: Claude only for now). The existing setup --app codex|opencode hook installs are left as they are.
  • brain.db is not committed to git (round 1).
  • No vector or embedding search. FTS5 keyword search only; embeddings stay a later option.

Prior art

obra/superpowers: one skill per method step, descriptions written to trigger, each skill naming the next, a one-paragraph bootstrap injected at session start, and plain markdown with no engine. We copy all of that except the "no engine" part. Claude Code plugins: .claude-plugin/plugin.json plus skills/, hooks/ and commands/, installed from a git marketplace.

The skills — high-level overview

Eleven skills in one plugin. Every SKILL.md is short: the trigger, the steps, the CLI commands it runs, and which skill comes next. Long material such as HTML component kits, worked examples and wireframe CSS moves into references/*.md next to it, loaded only when a step needs it.

brain

Triggers: any work in a repo with .brain/; "what's the state", "what's next".

Router: orient (brain, brain progress), the command map, the TOON/exit-code contract, and which phase skill fits. Replaces today's 31KB skill.

from: brain SKILL.md + init-brain · target ≤ 6KB · next: whichever phase fits

brain-start

Triggers: starting any non-trivial task, a bug, or a feature.

Frame intent and scope, read the relevant docs, brain check, brain verify --stage baseline, claim the feature, open a run note.

from: playbook start (9.5KB) · next: brain-grill (if a plan is needed) or brain-execute

brain-grill

Triggers: before any plan that carries a decision; "how should we…", "let's design…".

Memory check first (brain search, past decision rounds), then ask the open questions in rounds with recommendations, and wait for answers.

from: playbook grill (8.8KB) · next: brain-plan

brain-plan

Triggers: any plan, proposal or design review; "write up the plan".

Pick a tier, write the HTML artifact, brain review, run review poll in the foreground and loop until approved.

from: playbook plan (54.7KB) · SKILL.md ≤ 10KB + references/: sections.md, decision-cards.md, list-editor.md, diagrams.md, style.css · next: brain-execute

brain-product

Triggers: a plan for user-facing work (a CLI surface, an output shape, a screen, a workflow).

from: playbook product (23.1KB) · called by brain-plan

brain-ux

Triggers: a plan that adds or changes a screen.

Greyscale wireframes, a screen-state matrix (empty / loading / error / success), the user's journey through it.

brain-ai

Triggers: any work involving prompts, models, agents or evals.

A prompt contract, golden sets, a regression gate, the agent topology, model and eval-kind decision cards; brain evals.

brain-execute

Triggers: implementing an approved plan; "build it", "go".

brain-verify

Triggers: checking that a user-visible feature works; "verify", "test it in the browser".

An independent, skeptical walk of every acceptance criterion (golden path, error paths, edge probes), screenshot or transcript evidence, a verdict doc.

from: playbook verify (27.9KB) · references/: playwright-scaffold.md, verdict-format.md · next: brain-done

brain-done

Triggers: before saying a task is complete, opening a PR, or shipping.

Full brain verify, brain check, coherence (every changed path's doc updated), then close state: progress add, ship --evidence, pr.

from: playbook done (10.4KB) · terminal

brain-write

Triggers: writing anything into the brain (checkpoint, run note, feature doc, verdict, commit body).

The writing standard: specific, verbatim, dated; the 200-character summary gate; what never goes in.

from: playbook write (8.2KB) · used by execute and done

What stays in the CLI: brain playbook <id> becomes cat skills/brain-<id>/SKILL.md, a fallback for agents without skill support. Every help: line still names the next command. Gates (check, verify, ship) still exit 1. If a skill fails to trigger, the CLI output still points the agent to the right step.

The 4 slash commands (/start-task, /verify-done, /ship-feature, /harness-check) move into the plugin's commands/. They are explicit triggers for when a human wants to force a phase.

New installation instructions

Yes, it becomes a plugin. Two things get installed, and they version together (plugin version = npm version, enforced by skill --check).

Requirements

Node ≥ 24 (decision 6). No npm runtime dependencies; SQLite is built into Node.

Claude Code

# 1. once per machine: add the marketplace and install the plugin
/plugin marketplace add SeanningTatum/brain-axi
/plugin install brain@brain-axi

# 2. once per repo: create the brain (creates .brain/brain.db)
npx -y brain-axi init

# that's it: the plugin's SessionStart hook runs `npx -y brain-axi context`,
# and the 11 skills plus 4 commands are available in every session.
# update later with: /plugin update brain

What changes for existing users

  • brain setup --app claude detects the plugin. If the plugin is installed it removes the old settings.json hook to avoid a duplicate; if not, it points you to /plugin install.
  • Existing file-based brains keep working with no change (decision 4: no migration). brain init on a new repo creates the DB.

Technical decisions

5. What goes in the DB? settled in grill

Your pick: everything, docs included. Plan HTML files and screenshots still have to exist as files: the review server serves the HTML from disk and browsers load images by URL. The DB stores their path, hash and metadata, and review rounds and annotations become rows.

OptionProsCons

6. Node floor. changed since grill

You picked node:sqlite with ≥22.13. Then I tested it: Node 22.14 has no FTS5 and prints an ExperimentalWarning; Node 24.18 has FTS5 and no warning. FTS5 is the indexing you wanted SQLite for.

OptionProsCons
Indexing works on day one; no warning; one code pathUsers on 22 must upgrade (Node 24 is the current LTS)
Wider reachTwo search paths; warning on 22; search quality depends on Node version

7. Where brain.db lives, and how worktrees share it. changed in round 1

Round 1: don't commit the binary. brain.db is gitignored and local to the machine. That makes the shared-DB option the only way sub-agent worktrees see the same brain, since a fresh worktree has no DB at all. What it costs: state isn't shared through git (a clone or a teammate starts empty), CI has no DB to brain check, and backups are on you (open questions 2 and 3).

Prompt contract

The skills are the prompts. For each SKILL.md:

  • Job: make the agent take one phase of the method, then hand off to the next phase by name.
  • Inputs: the frontmatter description (≤ 300 chars; what triggers it), the body (≤ 10KB; ≤ 6KB for the router), references loaded on demand.
  • Output the caller relies on: CLI calls in the documented order, state written only through brain, and the next skill named in its last step.
  • Known failure modes: no trigger (the description is too vague), the wrong skill triggers (overlapping descriptions such as plan vs product), a skipped handoff, references never loaded.
  • Model pin: none. Skills must work on whatever model the host runs; the eval uses claude-sonnet-5-5 as the cheapest Claude that does real skill routing.

Eval plan + golden set

  • Existing skill-coverage (assertions, 37/37 at 1.000): retarget it from the single generated SKILL.md to skills/*/SKILL.md. Every command is named somewhere, the TOON contract is stated in the router, no tooling is invented. All frozen cases are kept.
  • New skill-routing (judge + deterministic): about 40 prompts mapped to the expected first skill. Typical: "plan X" → grill; "is it done?" → done. Edge: "quick fix" → start, not grill. Adversarial: "write a PR description" → none. Refusal-correct: no .brain/ → nothing triggers. Graded on whether the transcript shows the skill loading. Held-out: 8 cases. This suite has no baseline yet; building it is phase 2's first step.

Plan of record

  1. Phase 1 — skills become the source; no behavior change. Move each playbook's text verbatim into skills/brain-<id>/SKILL.md. brain playbook reads the files; playbooks.js becomes a thin index of ids and use_when. Acceptance: for every id, brain playbook output is byte-identical to before. Verify: diff all 10 outputs against a saved baseline; brain verify green; evals 37/37.
  2. Phase 2 — design them as skills. Write trigger descriptions and handoff lines; split plan, verify, ux and product bodies into references/; replace the 31KB brain skill with the router; brain context gets the bootstrap line. skill --check enforces size caps and requires every handoff target to exist. Acceptance: every SKILL.md is within its cap, context is ≤ 600B, skill-routing reaches ≥ 90% on non-held-out cases with frozen cases passing. Verify: wc -c; brain evals run skill-routing; skill --check exit 0.
  3. Phase 3 — plugin + install. Add .claude-plugin/plugin.json and marketplace.json, hooks/hooks.json and commands/. setup --app claude detects the plugin and removes the old settings.json hook. The plugin version matches the npm version. Acceptance: a clean CLAUDE_CONFIG_DIR can install from a local marketplace path and the next session shows the context line and the 11 skills; setup run twice is a no-op. Verify: transcript of the install, a fresh session, and both setup runs.
  4. Phase 4 — SQLite engine for new brains. Put a storage interface in lib/ with a files backend (today's code) and a sqlite backend (node:sqlite, WAL, schema + user_version migrations). init creates brain.db and adds it to .gitignore; worktrees resolve the shared DB (decision 7); then delete this repo's .brain and re-scaffold it with init, so dogfooding runs on the DB; engines bumps to the decision-6 floor; every brain check invariant also runs against the DB. Acceptance: the same command script over a file fixture and a DB fixture produces identical TOON, apart from documented path fields; check passes on both. Verify: a parity script runs both backends and diffs the output; two worktrees write at once with no lost rows.
  5. Phase 5 (gold) — indexing + bounded output. An FTS5 table behind brain search for DB brains: ranked results, snippet(), --section filter. Add the limits the 07-16 plan asked for to home, runs and docs listings. Acceptance: search on a seeded 5k-row brain returns in under 100ms; every listing is capped with a "more" help line. Verify: a timed search on the seeded fixture; listing outputs.
