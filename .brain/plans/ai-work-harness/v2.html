AI-work harness — evals, golden sets, prompt review

2026-07-28 · feature: ai-work (new, not yet created) · in-review · round 1

TL;DR

Today the harness assumes deterministic code: brain verify runs shell checks that pass or fail, and the playbooks talk about browser evidence. AI work has no such notion — a prompt change is a diff with no test. This plan adds an evals subsystem (.brain/evals/ + a brain evals verb + a new evals verify stage) and an AI branch through every playbook so planning an AI feature forces a golden set, an eval plan, and a regression gate before code is written. It also adds the human loop you asked for: checkpoints surface eval deltas, and brain evals review opens the existing review server on the last run so you can read the prompt and the per-case outputs and annotate them.

Round 1 update. All six decisions locked at the recommended option. Four open questions answered, which grew the plan in two places: agent-topology state is now in scope (phase 6 — the brain records which sub-agent/model owns which step), and portability is a first-class requirement — this has to work in cf-saas-react-router-starter with promptfoo + langchain, so the runner contract grows adapters instead of forcing every repo to hand-write an envelope.

Big picture

Three new nouns (prompt, golden set, eval suite) and one new loop. The agent writes prompts in the app repo; the brain holds the golden set, the run history, and the human's feedback on both.

The load-bearing idea: a failed eval case is not a bug report, it is a new golden case. The feedback file is the human's channel into both the prompt and the golden set, and it is the thing playbook done will refuse to let you skip.

1. Where do prompts live? The brain is state about the repo, not a copy of the repo — but eval review needs to show the exact prompt text that produced a run.

OptionProsCons
Prompts stay next to the code that sends them; no drift-by-copy; git history is the version history Review UI must read a repo path, and a moved file breaks the pointer (detected by brain check)
Self-contained; run snapshots always resolvable; version dirs are trivial App code importing from .brain/ inverts the harness relationship; every consumer repo must accept that
Exact reproducibility: every run stores the prompt it actually used Run files get fat; some duplication in .brain/

2. Who executes an eval? Scoring an AI output usually needs a model call. The CLI has zero deps and no API key.

OptionProsCons
Exactly the verify.json pattern already shipped; project owns model/keys/deps; brain stays zero-dep Every consumer repo must write a runner script and honor the envelope schema
Works out of the box, one less thing per repo Needs an SDK + API key in the CLI — breaks the zero-dep invariant; opinionated about provider
Zero infrastructure; works day one in any repo Not reproducible, not CI-able — the agent grading its own work is the failure mode evals exist to prevent

Note: recommended option still keeps brain evals record for agent-scored/manual runs — it is the escape hatch, not the default.

3. How does the harness know a task is AI work? The AI sections should not nag on a CSS fix.

OptionProsCons
Declared once, read everywhere (home, check, start, done, verify); machine-checkable One more field in the tracker; needs a migration default (kind absent = code)
Zero new state; agents can't forget to set a flag Playbooks are already long; irrelevant sections train agents to skim
No declaration at all Silent and wrong at the exact moment it matters — the first AI feature, before any prompt file exists

4. How strict is the regression gate? Evals are noisy; a gate that flaps gets disabled.

OptionProsCons
Regression cases (born from real bugs) are absolute; fuzzy rubric scores get slack for noise Two concepts to explain; needs a frozen: true flag per case
Dead simple, one number Flaps on judge nondeterminism; gets bypassed within a week
Never blocks; pure information Not a gate — regressions ship, which is the whole problem

  3. Phase 3 — execution + the gate. brain evals run <suite> shells the declared runner and appends to runs.jsonl; brain evals record --from <file> --adapter <name> ingests an externally produced result (native envelope or promptfoo output, per decision 8); brain evals golden add promotes a failure into a frozen regression case. New evals stage for verify.json so brain verify --stage evals runs suites and applies the gate — opt-in only, never folded into the default verify stage (round-1 answer: model calls cost money, so evals run when asked). brain progress add --eval <suite>=<score> writes the delta into the checkpoint, and the home dashboard grows an eval line that flags regressions, staleness, and unreviewed feedback.   4. Phase 4 — human eval review (the feedback loop). brain evals review <suite> generates a run artifact (prompt text at top, then one card per case: input, expected, actual, score, judge rationale; failures first) and opens it in the existing review server. Acceptance: Playwright walk with screenshots per playbook verify.
  5. Phase 5 — prompt registry. brain prompts / brain prompts view <name> over a registry mapping prompt name to repo path, model, owning feature, and linked eval suite. Runner envelope on stdout (the whole contract a consumer repo implements): {"cases":[{"id":"...","output":"...","pass":true,"score":0.9,"notes":"..."}]}. Same shape whether a script, a python eval framework, or an agent produced it — and per decision 8 a repo using promptfoo skips writing it entirely by naming "adapter": "promptfoo" and pointing at promptfoo's own output file.

Git policy (round-1 answer): everything is committed, including per-case outputs — the run history is the audit trail, and a run you cannot diff six weeks later is not evidence. Mitigation for size: per-case output truncated at a configurable max_output_chars (default ~4000) with the full text kept only when a case is frozen.
