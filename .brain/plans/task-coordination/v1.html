Task coordination — a unit of work below the feature

2026-08-06 · feature: task-coordination (proposed feat-009) · draft · round 0

TL;DR

brain-axi tracks features and checkpoints, but has no unit of work between them — so a plan's phases live only as prose inside its HTML artifact, and a coordinator handing phases to sub-agents has to hold that list in its own context, which is exactly the thing that does not survive compaction or a fresh session. This adds tasks as first-class, gate-checked state under each feature: a coordinator seeds them from an approved plan, workers claim them race-safely, closing one requires evidence the same way brain ship does, and brain check refuses to call a feature shipped while a task is still open. Doing it now because state-integrity just ran seven phases whose only record is CHANGELOG prose, and the feature is still marked in-progress days after its code merged and released.

Product brief

Problem + evidence

An agent asked to continue multi-phase work cannot find out from the harness what the phases are, which are done, or which one it should take next. Four pieces of live evidence, all re-runnable:

  • Seven phases, zero queryable records. grep "state-integrity phase" .brain/CHANGELOG.md returns 6 rows (phases 2–7; phase 1 is worded differently), and grep -c state-integrity .brain/runs/progress.md returns 8 mentions. No command answers “which phases exist and which are done” — a fresh session reconstructs it by reading prose.
  • The state is drifting right now. The latest checkpoint (brain progress, 2026-07-31) says “in-progress feature: none” while features/feature_list.json has feat-008 at in-progress with evidence: "". brain check reports 16/16 pass anyway, because a checkpoint is prose and prose is not checked. The feature's code merged as f6d9410 (PR #18) and released as bbab2cc (v0.2.0) — the harness still does not know it is done.
  • No prior art, so nothing to reuse. brain search "delegate" → 0 matches. brain search "coordinator" → 1 incidental hit in runs/progress.md:243 about a lightbox. The harness has never modelled handoff.
  • Parallel agents already happened, unattributed. features/planning-ux/verifications/2026-07-30.md:49: “Three runs, dispatched in parallel, each driving the app with its own script.” All three landed in one prose doc. runs append takes --step, --observed, --note and no author (bin/brain.js:1968) — there is no way to tell which agent wrote which step.

User + job to be done

Two agents, one job each.

The coordinator has just had a plan approved and holds its phase list in context. Its job is to get those phases done by other agents without becoming the only place the phase list exists — so that when its context is compacted, or the session ends and a different coordinator picks up, the work is still enumerable. Today its only durable options are a free-text checkpoint and a run note it must remember to write.

The worker is spawned cold with a one-paragraph prompt. Its job is to do exactly one phase and hand back something the coordinator can verify, without re-deriving the whole plan. Today it either gets brain playbook start (read the entire brain, ~4 commands, no idea which slice is its own) or whatever the coordinator remembered to paste into the prompt — and if the coordinator paraphrased an approved decision wrong, the worker has no way to notice.

Success metric

Tier 2, countable proxy. Baseline (measured today): answering “which phases of state-integrity exist, which are done, and is the feature closeable” took 7 CHANGELOG rows + 8 progress.md mentions + git log + a feature doc read, and produced the wrong answer from the harness itself (check 16/16 while the tracker and the latest checkpoint contradict each other). Target: for the next multi-phase feature, one command — brain tasks <slug> — answers all three, and brain check emits a failing row when a feature is shipped with an open task. Observed by: running both commands at that feature's close; the check row is a pass/fail, not a judgment.

Non-goals

  • Spawning agents. A reader seeing the word “coordination” will reasonably expect orchestration. brain-axi will not launch, schedule, or supervise a sub-agent — the harness (Claude Code, Codex, opencode) owns spawning, and a CLI that shelled out to one would bind this tool to one vendor's agent runner. brain holds the state the agents coordinate through; the prompt is still the coordinator's job.
  • Relaxing one_in_progress_at_a_time. Features stay strictly serial (bin/brain.js:785). Parallelism arrives one level down, inside the single in-progress feature. Letting two features run at once is a scope-discipline change this plan is not making.
  • Parsing phases out of the plan HTML. Tempting — the phases are right there in section 10 of every plan artifact — and declined: an HTML scrape would silently mis-seed on any plan whose markup drifts, and a wrong task list is worse than no task list. The coordinator types the tasks; the approved decisions are read from reviews.jsonl, which is already structured.

Scope tiers

Thin — the record and the gate.

Ships: tasks schema in lib/state.js, per-feature tasks.json, brain tasks (list / add / claim / done / release), compare-and-swap claiming, 2 new brain check rows, ship preflight refusing on an open task.

Costs: phases 1–2.

Leaves on the table: no handoff brief (workers still get a hand-written prompt), no author attribution on run steps, no playbook telling anyone this exists.

Complete — the handoff.

Ships: thin, plus brain brief <slug> <task> (the task, its acceptance criteria, the approved decisions from reviews.jsonl, and the rules that own the files it touches, in one TOON payload a cold worker can act on), runs append --task --author, the execute playbook rewritten as a coordinator/worker loop, and a regenerated skill.

Costs: phases 1–4.

Leaves on the table: brain watch's dashboard shows feature status but not task status, so the human still reads the CLI to see fan-out progress; no telemetry on task duration or rework.

Gold — the human's view and the numbers.

Ships: complete, plus a tasks panel in brain watch (per-task status, owner, elapsed, evidence) and task lifecycle events appended to runs/gates.jsonl so brain metrics reports tasks-per-feature and reclaim rate.

Costs: phases 1–6.

Leaves on the table: nothing this plan identified. Note that the dashboard panel is a screen — approving gold means phase 5 opens a brain playbook ux round for wireframes and screen states before it is built. This plan deliberately does not mock a screen it may not be authorized to add.

Prior art

Inside this repo: brain plans lists 9 plans, none of which proposed a sub-feature work unit — the closest is 2026-07-31-harness-hardening, which produced today's lib/state.js schema and atomic-write path, and which this plan extends rather than rebuilds. brain search "delegate" returns 0 matches and "coordinator" returns 1 unrelated hit, so there is no existing convention to honor or contradict. brain features shows no cut feature covering this ground; feat-004 annotation-watch (planned) is a post-ship feedback runner, adjacent but not overlapping.

The mechanism being borrowed is lib/state.js's own contract, as documented in rules/state.md: one definition per invariant, validators returning null or one message naming the exact bad field (tasks[2].status), never throwing, all durable writes through writeFileAtomic, and read-compat/write-new for new required fields. A task record that did not follow that contract would reintroduce the exact class of defect feat-008 just closed.

Context

Per brain features, feat-008 state-integrity is the current in-progress feature and the immediate blocker: its slot must be freed before feat-009 can be claimed, because policy.one_in_progress_at_a_time is in force. Its code is already merged (f6d9410) and released (bbab2cc, v0.2.0); what is missing is the closing paperwork, which is being produced in parallel with this plan — a verification doc and an evidence string, after which brain ship state-integrity frees the slot.

The 2026-07-31 checkpoint closes with “STOP auditing — reviewer's own call” and names cutting a release as the highest-value next action. That release is cut. This plan is the next thing, and it is deliberately not more auditing: it adds a missing state layer rather than hardening an existing one.

One unrelated fact worth surfacing because it affects every npx path this plan's skill regeneration would emit: npm view brain-axi still returns 404. v0.2.0 is tagged but unpublished. That is launch-readiness territory, not in this plan's scope, but any doc this plan writes using npx -y brain-axi is currently aspirational.

Big picture

Agent topology

This plan introduces no prompt, no model call, and no eval — the CLI stays deterministic, so the prompt-contract and eval-plan sections of brain playbook ai do not apply. The topology table does, because the feature's whole purpose is a handoff contract between roles, and every phase below names the role that owns it.

RoleModelOwnsHandoff contractEscalation rule
Coordinator the session's own model (Opus-class) Seeding tasks from the approved plan; deciding fan-out; the final brain ship Out: a brain brief payload per worker. In: each worker's evidence string Never edits a file a worker holds a claim on; if two workers' evidence conflicts, re-opens the task rather than picking a winner
Worker Sonnet-class Exactly one task, start to evidence In: brain brief. Out: brain tasks done --evidence composed only from observed output On a CAS conflict: re-list and take another task, never force. On acceptance criteria it cannot meet: report back, do not redefine the task
Auditor optional Sonnet-class, read-only tools Adversarially checking one completed task's evidence against its acceptance criteria In: task id + evidence. Out: confirmed / refuted with a file:line citation Refutes by default when it cannot reproduce the evidence

Product decisions

P1. Can a fresh agent ask the CLI which phase to work next, or must it read the plan artifact?

This is the whole feature stated as one question. Everything below it is mechanism.

OptionProsCons
Survives compaction and session death; a gate can read it; the answer is one command A second place the phase list lives, which can drift from the plan artifact unless seeding is deliberate
One source of truth, zero new state, zero new commands Exactly today's failure: the phase list is prose, unqueryable and ungateable — the 7-phase state-integrity record is the evidence

P2. Should two agents be able to hold work at the same time?

OptionProsCons
Matches how the work already happens (three parallel verification runs, 2026-07-30); scope discipline is preserved one level up Needs race-safe claiming — without it two workers silently overwrite each other's task record
No concurrency to get wrong; claiming becomes trivial Gives up the main reason to coordinate at all; a 7-phase feature stays a 7-session feature

P3. Should closing a task require evidence, the way brain ship requires it for a feature?

OptionProsCons
A worker's report becomes checkable instead of a claim; consistent with the rule the ship gate already enforces A worker with nothing observable to quote is blocked — arguably correct, but it is friction
Lighter for mechanical tasks (a rename, a doc edit) Reproduces the shape feat-008 existed to kill: a status that says done with nothing behind it

P4. Which scope tier ships?

OptionProsCons
The brief is what makes a cold worker cheap; without it the record exists but nobody uses it 4 phases; the human still reads the CLI rather than the dashboard to watch fan-out
Smallest thing that fixes the drift; shippable alone No playbook mentions tasks, so agents will not find them
The human sees fan-out live; reclaim rate becomes a number Phase 5 is a screen — needs its own UX round before it can be built

Decisions needed

T1. Where does the task record live?

This is a concurrency question disguised as a layout question: writeFileAtomic is temp-plus-rename, which makes a write all-or-nothing but still last-writer-wins. Two workers touching the same file lose a write.

OptionProsCons
Blast radius is one feature; keeps feature_list.json — the hottest file in the brain, read by every command — out of the concurrent write path; sits next to the feature's runs and verifications A second schema and a second validator to keep coherent with feature_list.json; brain check must walk features to find them
One file, one schema, one atomic write path already validated by brain check's first row Every parallel worker writes the file every other command reads; a lost write there corrupts the feature tracker itself, not just a task list
Writes never collide at all — each worker owns its own file Ordering and dependencies have nowhere to live; listing means a directory walk plus N parses; no single place to validate

T2. How is a claim made race-safe with zero dependencies?

OptionProsCons
No stale state to clean up — the file is always the truth; the loser gets exit 1 and a help: line telling it to re-list and retry; ~20 lines using node:crypto A losing worker burns one command round-trip; the read-modify-write window is small but nonzero (no OS-level guarantee)
mkdirSync failing EEXIST is genuinely atomic on every POSIX filesystem A worker that dies holding the lock wedges the feature until someone deletes a directory; a TTL means guessing how long a task takes
Nothing to build Two workers both believe they own the task and both do the work; silent, and the failure surfaces as a confusing double commit

T3. How hard does brain check gate on tasks?

rules/state.md sets the precedent: read-compat first, strict a release later, and --strict is always on at the ship gate.

OptionProsCons
Follows the read-compat/write-new rule — every existing brain and every consuming repo keeps passing; the one invariant that actually matters (a feature cannot be done while its work is not) is a hard gate from day one A feature can still ship with an empty task list, i.e. nobody is forced to use the feature
Makes the feature real rather than optional Turns a one-commit feature into a ceremony; --strict is the ship gate, so this would block trivial features on inventing a task
Zero risk to existing repos An advisory nobody reads is the decaying-gate pattern rules/state.md names as the thing to avoid

T4. What goes into brain brief, and where does it come from?

OptionProsCons
Every part already exists and is already parsed — plans view reads the decision prompts today; nothing new to maintain, nothing invented The rules-for-touched-files mapping needs a declared files field per task, which is one more thing the coordinator must fill in
Maximum flexibility; no derivation logic Reintroduces the paraphrase risk this is meant to remove — the worker reads the coordinator's summary of an approved decision instead of the decision
Nothing to build; the existing playbook already orients an agent playbook start orients to the whole brain, not to one slice — the worker still has to be told what its task is by prompt

T5. What happens to a claim held by a worker that died?

OptionProsCons
No guess about how long a task should take; the coordinator sees “held 40m” and decides; matches the harness's stance that state changes are deliberate A dead worker's task stays held until someone looks
Self-healing with no coordinator attention Any TTL is wrong for some task; expiring a live worker's claim mid-edit is worse than a stuck one

Plan of record

Tier boundaries land on phase boundaries: thin stops after 2, complete after 4, gold after 6.

  1. Phase 1 — the record. Owner: coordinator. Add TASK_STATUSES, validateTasksShape, tasksPath and a compare-and-swap write helper to lib/state.js; add cmdTasks (list, add, claim, done, release) to bin/brain.js. Acceptance: tasks round-trip through a scratch brain; every subcommand rejects unknown flags and ends in a help: list; validateTasksShape names the exact bad field (tasks[2].status) and never throws; new assertions in scripts/check-state-invariants.mjs pass.
  2. Phase 2 — the gate. Owner: coordinator. Two brain check rows (task schema parses; no shipped feature has an open task), ship + set-status shipped preflight refusing on an open task, absent tasks.json passing everywhere. Acceptance: a planted open task makes brain check exit 1 with the feature and task named, and makes brain ship refuse and write nothing (feature_list.json byte-identical before and after); brain check on this repo stays at 16 passing rows plus 2 new ones.
  3. Phase 3 — the handoff. Owner: coordinator. brain brief <slug> <task-id> composing task + acceptance + the approved decision prompts from plans/<slug>/reviews.jsonl + the rules docs owning the task's declared files; runs append gains --task and --author. Acceptance: brief output for a real task fits in one screen, cites at least one decision verbatim from reviews.jsonl, and a run step written with --task --author shows both in runs view.
  4. Phase 4 — teach it. Owner: coordinator. Rewrite the execute playbook as a coordinator/worker loop with the topology table; add tasks + brief to skillContent(); update rules/state.md and rules/cli-commands.md; regenerate the skill. Acceptance: brain skill --check exits 0, brain verify 4/4 including skill-sync and playbook-refs, and the execute playbook names which role runs each command.
  5. Phase 5 — the human's view. Gold tier only, and gated: a tasks panel in brain watch is a screen, so this phase opens a brain playbook ux round for wireframes and screen states (empty, one task, fan-out in flight, stale claim) before any code. Acceptance: the approved wireframe exists as a plan artifact section, then the panel matches it in a screenshot.
  6. Phase 6 — the numbers. Gold tier only. Append task lifecycle events to runs/gates.jsonl; brain metrics reports tasks per feature, median hold time, and reclaim rate. Acceptance: metrics reads real events written by a real fan-out, not synthesized rows.
Why not build the brief first and the record second?

A brief with nothing to brief about is a prompt template. The record is what makes the brief derivable rather than authored, so it has to exist first — and the gate has to exist before anyone relies on the record, or the first drift goes unnoticed exactly the way feat-008's did.

Testing plan

This repo has no test framework by policy; the test surface is scripts/check-state-invariants.mjs (a plain assertion script, already at ~186 assertions and already wired into CI). Every box below is an assertion there unless it says otherwise.

Open questions

  • Should a task be able to depend on another task, or is a flat ordered list enough? Feature-level dependencies already exist and are checked; task-level ones would need their own cycle detection.
  • Does a worker's claim need to record the git branch or worktree it is operating in? Parallel workers editing the same repo is the real hazard, and brain has no view of that today.
  • Should closing the last task auto-run brain ship, or stay explicit? Auto would be convenient and would also let a worker ship a feature the coordinator has not reviewed.
  • Does a task's evidence deserve a commit receipt, the way a strict verification verdict now does? That would bind a worker's claim to code that actually landed.
