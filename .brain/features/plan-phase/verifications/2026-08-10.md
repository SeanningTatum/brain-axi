## Error paths

Each planted deliberately against a throwaway brain; each proves an enforcement, not a message.

### E1 — a summary over the cap is refused (exit 2), and nothing is written

```
$ node bin/brain.js progress add --summary "<260 x's>"
error: --summary is 260 chars; the cap is 200
help[4]:
  progress.md is a rolling cursor — one line. Verbatim output belongs in the run note.
  Headline only: brain progress add --summary "<what changed, one line>" --next "<next concrete action>"
  Detail goes to: brain runs append <slug> --step "..." --observed "<verbatim output>"
  Run `brain playbook write` section 4 for the slots per artifact
exit=2
```

The refusal teaches the fix rather than only denying it — an agent that cannot see where the detail
belongs retries with a slightly shorter paragraph.

### E2 — the boundary is exercised from both sides

| Input | Expected | Observed |
|-------|----------|----------|
| exactly 200 chars | accept | exit 0, entry lands |
| 201 chars | refuse | exit 2 |
| 600 chars | refuse | exit 2 |
| ordinary summary | accept | exit 0, `progress.md` contains it |

A cap tested only from the failing side can be off by one in the direction that silently rejects
legitimate input.

### E3 — two refusals leave `progress.md` byte-identical

Asserted by reading the file after an accepted write, then again after both refusals, and comparing
the two strings. A partial write here would corrupt the cursor every session reads first.

### E4 — an unknown playbook id fails and lists the real ones

```
$ node bin/brain.js playbook grillz
error: no playbook "grillz"
help[1]: known playbooks: start, grill, plan, product, ux, ai, verify, execute, done, write
exit=1
```

### E5 — the new assertions were verified to fail against a broken gate

The gate was disabled in place (`if (false && flags.summary.length > SUMMARY_MAX_CHARS)`) and the
suite re-run. Exactly four assertions went red:

```
  progress add refuses one char over the cap — exit 0
  progress add refuses a paragraph-length summary — exit 0
  the refusal names the cap and points at runs append — <the accepted checkpoint echoed back>
  two refused summaries leave progress.md byte-identical — a rejected entry reached the file
```

Restoring the condition returned the suite to 419/419. A gate with no failing fixture is a claim,
not a check.

### E6 — internal callers are not caught by the gate

`brain ship` and `brain pr` compose their own summaries and cap the interpolated value at 120 before
calling `appendProgressEntry`, which the gate does not touch — it is scoped to the `--summary` flag
a caller types. This feature's own ship is the live proof: it was shipped with an evidence string
longer than 200 characters and its checkpoint landed normally. Had the gate been placed in
`appendProgressEntry` instead, that ship would have failed.

## Limitations

- **The 200-character cap is a judgement, not a measurement.** It is roughly two terminal lines and
  comfortably longer than any headline in this repo's history, but no study produced the number. It
  is one edit in `lib/state.js` if it proves wrong.
- **The gate cannot check quality, only length.** A 199-character sentence written in the wrong
  register passes. `playbook write` is the standard; the cap only removes the most mechanical
  failure.
- **Neither new playbook is enforced by anything.** Nothing checks that a plan was grilled, or that
  a feature doc follows the slots. Phase 4 would have been the first such row and was deferred;
  until something scores it, "the register improved" is an unmeasured claim. The plan's own open
  questions say so.
- **The success metric has one data point.** "Share of decisions landing off the recommendation" was
  0/13 before and, on this plan's round 2, 0/7 again — though three of those seven were
  confirm-a-citation rather than a choice, and the one card carrying genuinely new information
  (scope tier) went unanswered in that round and was settled in conversation afterwards. One plan is
  not a trend.
- **The grill has never been run cold.** It was simulated inside a review session on the plan that
  proposed it, by the agent that wrote it. Its first honest test is the next plan.
- **Phase 4 is deferred, not cut.** It stays in the plan of record.

419/419. `verify --stage baseline` 4/4, `check` 18/18, `check --strict` clean, `skill --check`

omitted — in particular, nothing yet measures whether the register standard works, and the grill has
not been run outside the plan that proposed it.
