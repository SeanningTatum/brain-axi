# Verification: task-coordination — a unit of work below the feature

_Date: 2026-08-06 · Feature: feat-009 · Branch: `chore/ship-state-integrity`_

## What was verified

The four phases approved at the **complete** tier of plan `task-coordination` (round 1,
2026-08-06): the task record and `brain tasks`, the gate rows and gated autoship, `brain brief` and
`runs append --task/--author`, and the coordinator/worker rewrite of the `execute` playbook.

This is a CLI/state-layer feature with no UI, so the house verify playbook's screenshot walk is
adapted to verbatim terminal transcripts. There are no screenshots and no mockups to reconcile —
the approved plan is a text/decision-card plan.

The feature was **dogfooded on itself**: after phase 1 was bootstrapped by hand (it builds the
tool, so it could not use the tool), phases 2, 3 and 4 were seeded as real tasks in
`features/task-coordination/tasks.json` and worked by separate worker agents through
`brain tasks claim` / `brain brief` / `brain tasks done`. Every transcript below is from that run
or from a throwaway copy of `.brain` in a scratch directory.

## Defects found and closed during the build

Recorded because the feature's own `EVIDENCE DISCIPLINE` playbook section is derived from them.

| # | Defect | How it was found | Status |
|---|--------|------------------|--------|
| 1 | A hash compare followed by a write is not a compare-and-swap: two concurrent claims both won in 5/5 measured trials, one claim silently discarded | A worker flagged it; reproduced independently before acting | Fixed — CAS inside an `O_EXCL` lock |
| 2 | The first lock had no ownership: the `finally` unlinked by path, so a holder whose section overran the stale threshold deleted a LATER holder's live lock, putting two processes in the critical section | Adversarial audit; reproduced in three moves | Fixed — ownership token, release-only-if-mine, pre-write ownership re-check |
| 3 | `FEATURE_FIELDS` declared in `lib/state.js` and re-declared in `bin/brain.js`, violating the one-definition rule `rules/state.md` names | Coordinator read the diff after a worker reported "reused" | Fixed — imported |
| 4 | The hex-commit pattern copied rather than shared between `parseReceipt` and `validateTasksShape` | Same, one phase later | Fixed — shared `RECEIPT_COMMIT_RE` |
| 5 | `runs append <feature>` wrote to `features/<slug>/runs/` while `runs view` only read the legacy `.brain/runs/` pool — notes written by `runs append` were unreadable from the day feature-scoped notes were added | Phase 3 worker tried to satisfy its own acceptance criterion | Fixed — both pools merged, `--feature` disambiguates |
| 6 | A feature slugged like a verb was unreachable: `brain tasks release` parsed as the verb, then failed for a missing `<slug>` | Adversarial audit | Fixed — a verb requires a following positional; `list` documented |
| 7 | `receipt` validated with no `commit` key — proof binding a claim to nothing | Adversarial audit | Fixed — `commit` required whenever a receipt is present |

Every fix in rows 1, 2 and 6 has an assertion that was **verified to fail against the reverted
implementation** before being accepted — 4 assertions for row 2 (`7 winners across 5 trials` when
reverted), 3 for row 1.

## Limitations

- **The residual lock window is real and documented, not closed.** Between the final ownership
  check and the rename there is a microsecond-scale window with no fsync in it. Closing it entirely
  needs fencing tokens and a lock service, which a zero-dependency CLI writing JSON files does not
  get to have. The comment in `lib/state.js` says so plainly rather than claiming safety it cannot
  provide.
- **`LOCK_STALE_MS` is 60s and untested at that duration.** The stale-breaker is asserted by
  backdating a lock's mtime, not by holding a real 60-second critical section. The assertion proves
  the breaker's logic; it does not prove 60s is the right number.
- **Phases 5 and 6 (the `brain watch` tasks panel and task telemetry in `brain metrics`) are not
  built.** They are the gold tier and were deferred at review, not cut. Phase 5 is a screen and owes
  a UX round before any code.
- **The approved decision text for race-safety is now partially out of date.** The plan says
  "compare-and-swap on a content hash; loser retries", which is still the semantic but not the whole
  mechanism. `rules/state.md` carries the accurate version; `brain brief` will keep quoting the
  original decision verbatim, which is correct — a decision of record should not be silently
  rewritten by what implementation later taught.
- Autoship was exercised against an unverified feature (refusal) and, in throwaway brains, against a
  verified one (success). It has not yet fired for real on a genuinely shipping feature.

## Verdict

**Verdict**: PASS — all four approved phases are implemented and enforced from real gate paths, not
merely present. 409 assertions (from 222), `check` 18/18, `check --strict` 21/21, `verify` 4/4,
`skill --check` clean. Every error path attempted proved an enforcement: an open task blocks the
ship with bytes unchanged, a dependency cycle is named at both ends, a task cannot close without
evidence, and two concurrent claims through the real CLI produce exactly one winner in 3/3 trials.
Seven defects were found and closed during the build, three of them by adversarial review of work
that had already reported success — and the assertions covering the two concurrency defects were
verified to fail against the reverted code before being accepted. Limitations are stated above
rather than omitted; none of them contradict a claim made here.
